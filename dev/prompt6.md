你现在是一位顶级的系统架构架构师和专业的Rust工程师。我们的目标是构建 Kite：一个能在高性能计算机里在 count（计数）和 dump（转储）阶段全面超越 KMC3 的极速软件。我们的测试标准是48线程和内存限制为64GB。 kite count读取fastq.gz或者fastq或则和fasta, fa, fq, fasta.gz等文件，转变成.kite二进制文件，然后kite dump将二进制文件转变成kmer, count两列的表格，整个过程类似KMC。但kite在高性能计算机上能充分利用强大的CPU和高内存，来得到极限的速度，极短的运行时间。

## 1. 核心设计哲学：暴力美学
- 拒绝 HashMap: 在 48 线程下 HashMap 的随机访问会导致缓存行失效和内存墙瓶颈。我们采用 分桶 (Binning) + 排序 (Radix Sort) 。
- 硬件压榨: 强制使用 CPU 亲和性绑定、io_uring 异步 I/O、SIMD 指令集 。
- 数据流式丢弃: 尽早丢弃 FASTQ 的 ID 和质量值(解压后就直接丢弃ID和质量，只使用序列信息)，仅保留 2-bit 编码的序列信息 。
- 每个子命令都要加--test-mode参数，这个参数会打印极其详细的每个模块的运行指标，便于AI工具观察后进一步进行迭代。

## 2. 项目结构 (src/)
严格遵守以下目录划分，保证模块独立性：
- src/format/: 定义 .kite 二进制格式及共享的 2-bit 编码逻辑。
- src/count/: 子命令文件夹。处理输入、SIMD 提取、分桶、排序。
- src/dump/: 子命令文件夹。败者树合并、TSV 序列化、异步写入。
- src/main.rs: 子命令分发。

## 3. .kite format (2-bit & Format)
1. **2-bit SIMD 转换**: 使用位运算 `(c >> 1) & 3` 快速转换 ACGT，跳过 N。使用 AVX2/AVX-512 指令一次性处理 32/64 个碱基 。
2. **.kite 格式定义**: 
   - Header: Magic, K-size, BucketCount.
   - IndexTable: 每个分桶在文件中的偏移。
   - Data: 连续的 `(u64_kmer, u32_count)` 原始内存块。
   - 采用 repr(C) 布局。使用 bytemuck 实现零拷贝序列化 。

## 4. kite count
`count` 的输入读取采用字节流状态机，不把 FASTQ 四行记录转换成 `String`。序列行直接进入批量缓冲，再进入 k-mer 滑窗提取。优化：直接跳过 ID 和质量值行，只提取序列信息。

| `k` 范围 | 表示 |
|---|---|
| `k <= 31` | `u64` 热路径 |
| `32 < k <= 64` | `u128` 热路径 |
| `k > 64` | packed words |

1. **CPU 绑定**: 使用 core_affinity 将 48 个线程精准绑定到 48 个 CPU 核心。如果参数里--threads给别的线程数，同样进行绑定。关键结构体应用 #[repr(align(64))] 填充，防止多核竞争下的 伪共享 (False Sharing) 导致性能崩塌。
2. **异步读取与解压**:
   - 使用 `monoio` 的 `io_uring` 异步读取 `bgzip` 文件。
   - 利用 `noodles-bgzf` 的 block 偏移，多线程并行解压独立块。分配线程并行解压不同的 BGZF 块。解压后的数据直接流入预分配的循环缓冲区 。
3. **均匀分桶 (Partitioning)**:
   - 计算 Minimizer，并应用 `MulSwapMul` 哈希函数消除 Poly-A 带来的倾斜 [11]。
   - **自适应分桶**: 预分配 64MB 的桶缓冲区。若检测到某个桶偏斜严重，动态重新分片以保证 64GB 内存不崩。
   - 
4. **Hashed Radix Sort (MSD)**:
   - 在内存缓冲区满时触发最高有效位 (MSD) 基数排序。实现滑动窗口计算 Minimizer，并应用 MulSwapMul 哈希函数以消除低复杂度序列导致的倾斜 。根据哈希值将 k-mer 分配到 $2^{10}$ 至 $2^{12}$ 个桶中。每个桶配备一个 64MB 的缓冲区。当缓冲区满时，使用 io_uring 的 WRITEV 异步写入 .kite.bin 中间文件 。内存控制：通过信号量监控 64GB 内存使用情况，若缓冲区占用过高，暂停读取线程。
   - **软件预取 (Software Prefetching)**: 在排序循环中手动发射 `_mm_prefetch` 指令预取 20-30 个元素后的目标内存地址，掩盖主存延迟 [13, 14]。
   - **NUMA 感知内存分配**: 高效的计数器必须实现 NUMA 感知的缓冲区分配，确保每个处理线程访问的内存页面与其所在的 CPU 核心在物理上属于同一个内存控制器 。
5. 为了进一步榨取硬件性能，计数器k可以引入协程（Coroutines） 。通过在单个线程内管理成千上万个协程任务，每个协程负责一个 I/O 请求的后续计算，可以有效避免传统线程池带来的昂贵上下文切换和锁竞争 。

这个设计的核心是：**不要在 `count` 阶段做沉重的全局合并**。全局合并对吞吐非常不友好，而且容易把 CPU 和内存都拖进大量随机访存。


## 4. kite dump 

1. **败者树 (Loser Tree) 合并**: 
   - 实现败者树合并数以百计的已排序桶文件。
   - 比较复杂度从 $2 \log K$ 降至 $\log K$ [15, 16, 17]。
2. **TSV 序列化**: 
   - 禁止使用 `println!`。
   - 使用 `itoa` 将 Count 直接写入 128KB 的页对齐缓冲区。
   - 使用 `io_uring` 异步、大块地顺序写出 TSV。
3. **按 bucket 并行**
   - 每个 bucket 独立处理，能更容易吃满多核。
4. **动态 entry 宽度**。`k<=31` 的 segment 可以更紧凑，降低读写和解码成本。
5. **分批写出**。避免一次性把全部 bucket 输出堆到内存里，降低峰值和写阻塞。

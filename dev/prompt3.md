三、必须坚持的设计哲学

这是本项目最重要的指导原则：

1. 速度优先，而不是保守省内存

目标机器是高性能服务器，不是低配笔记本。
不要用“为了省内存而让速度变慢”的思路主导设计。

具体原则：

愿意使用较大内存来换速度
能用 64 GB 就不要只用 8 GB
小样本尽量留在内存内完成
大样本采用流式 + 分层 spill，但仍要尽可能利用内存做更多局部聚合
2. count 阶段不要执着于做最终全局合并

如果全局合并非常重，会拖垮 count。
count 的首要目标是：

高效读入
高效提取 k-mer
高效局部聚合
高效按 partition 输出中间结果

必要的最终全局归并可以后移到 dump。
也就是说：

count 负责高吞吐地产生高质量中间结果
dump 负责必要的最终整理和输出
3. 避免通用 HashMap 成为主路径

不要把“每看到一个 k-mer 就扔进 HashMap +1”作为默认核心策略。
这通常会带来：

随机访存
cache locality 差
rehash 成本
内存碎片
多线程扩展性差

默认主路径应该优先考虑：

整数编码
分桶
连续内存 buffer
桶内排序
RLE 聚合
按 partition 输出中间段
延迟最终 merge 到 dump
4. 尽量减少小文件风暴

spill 路径不能产生海量小文件。
必须通过设计减少：

每个 worker × 每个 partition × 每次 flush 造成的碎片
超大 fan-in merge
频繁 open/close
文件系统元数据压力
5. 避免“为了抽象优雅而牺牲速度”

不要为追求过度泛型、优雅抽象、层层 trait 封装而损失热路径性能。
热路径可以更直接、更专用、更硬编码一些，只要：

结构清晰
注释清楚
可测
可维护

五、输入与支持范围

Kite 必须高效支持以下输入：

未压缩 FASTQ
普通 gzip 压缩 FASTQ (.fastq.gz, .fq.gz)

应尽量采用字节流状态机解析

六、k-mer 处理要求

Kite 优先支持：

k = 21
k = 31
k = 51

请为这些场景做专门优化，而不是只写一个完全通用但很慢的泛化实现。

表示要求
对 k <= 31

优先使用：

2-bit 编码
u64 表示
尽量走专门优化路径
对 k = 51

优先考虑：

2-bit 编码
u128 表示
canonical k-mer

应支持 canonical k-mer 逻辑（正向/反向互补取较小者），并在热路径中尽量降低分支和开销。

非 A/C/G/T 字符

必须正确处理。
遇到非法碱基时，应重置滑动窗口，避免错误 k-mer。

七、推荐的主算法方向

请重点考虑以下总体路径，并根据现有项目结构整合进去：

主路径建议：分桶 + 连续内存 + 桶内排序/RLE + 分段输出
count 阶段推荐流程
大块读取输入
流式解压
FASTQ 字节级解析，仅保留序列
序列转 2-bit 编码并提取 canonical k-mer
按 partition 策略把 k-mer 分发到本地桶
每个 worker 为每个 partition 维护连续内存 buffer
当某个桶达到阈值时：
对桶内 k-mer 排序
执行 RLE 聚合
生成已排序/已聚合的 segment
segment 写入 partition 对应的中间文件或分层中间结构
尽量不在 count 阶段做沉重的全局总合并
count 输出一个适合 dump/query/histo 后续利用的高效中间格式
dump 阶段推荐流程
读取 count 产生的 partitioned segments
对每个 partition 做归并
如 segment 已排序/已聚合，则采用高效 merge
生成最终 text dump 或其他输出格式
八、并行模型要求

目标不是“有多线程”，而是真正让多线程吃满机器。

请重点优化：

1. 大块 batch 传递

不要在线程之间传单个 read 或单个 k-mer。
线程之间应传：

大块字节 buffer
大块解析结果
大块 partition batch
2. 尽量线程本地化

尽量让 worker 持有本地状态，例如：

本地 sequence 解析缓冲
本地 k-mer 提取缓冲
本地 partition buffers
本地排序工作区
本地 spill 缓冲

减少跨线程共享写。

3. 避免过细粒度 channel 消息

消息过碎会有很大调度开销。
请优先使用：

粗粒度批量任务
固定大小或自适应大小 chunk
较少同步点
4. count 阶段 CPU 利用率必须作为核心指标

请把目标设为：

在 48 线程 / 96 逻辑线程服务器上，count 不应只跑到几百 % CPU
应尽量接近真正的高并行吞吐
行为上应更像 minimap2，而不是“名义多线程，实际只在少数阶段并行”

# Kite Design Notes

本文档是当前阶段的工程重建说明。此阶段只保留 `count` 和 `dump` 两个子命令；其他子命令不在本轮范围内。

## 1. 目标

Kite 这一阶段的唯一目标，是在 48 线程、64GB 内存限制下，把 HG002 场景的 `count + dump` 总时长尽可能压低，并在 `k21 / k31 / k51` 上持续压过 KMC。

设计原则只有四条：

1. `count` 优先，`dump` 次之，但两者都必须保持高速。
2. 只做对吞吐真正有帮助的结构优化，不回到 HashMap 路线。
3. `count` 输出要尽量紧凑，减少后续 `dump` 的解码和归并压力。
4. 任何新优化都必须能回到 test-mode 指标上做 A/B 对比。

## 2. 当前范围

当前重建范围只包括以下模块：

| 模块 | 职责 |
|---|---|
| `src/count` | FASTQ -> `.kite`，负责读取、解析、k-mer 编码、分桶、局部排序、RLE、分段写出 |
| `src/dump` | `.kite` -> TSV，负责分段并行解码、归并和文本写出 |
| `src/kite/format.rs` | `.kite` 二进制格式、segment 读写、index/footer |
| `src/core/lut.rs` / `src/core/bitops.rs` | 2-bit 编码、反向互补、位运算基础 |

这一阶段不考虑 `info / query / histo / merge / profile / sketch` 的新能力，也不把它们作为优化目标。

## 3. `count` 设计

### 3.1 输入路径

`count` 的输入依然采用字节流状态机，而不是把 FASTQ 四行记录转换成 `String`。序列行直接进入批量缓冲，再进入 k-mer 滑窗提取。

对未压缩 FASTQ，直接按字节流读取。对 gzip / BGZF 输入，保持流式读取和块级解压，不把整文件抬进内存。

### 3.2 k-mer 表示

当前按 `k` 分层处理：

| `k` 范围 | 表示 |
|---|---|
| `k <= 31` | `u64` 热路径 |
| `32 <= k <= 64` | `u128` 热路径 |
| `k > 64` | packed words |

`k<=31` 是当前最重要的优化对象，因为 HG002 的 short-read 场景里它最常见，而且它对排序、写盘和 `dump` 的连锁影响最大。

### 3.3 分桶与局部聚合

当前主路径是：

1. 大块读取输入。
2. 滑窗提取 k-mer。
3. 按 partition 分桶。
4. 桶内连续 buffer 累积。
5. 达到阈值后执行桶内排序和 RLE。
6. 生成 segment 写入 `.kite`。

这个设计的核心是：**不要在 `count` 阶段做沉重的全局合并**。全局合并会把吞吐拖进大量随机访存，并把后续 `dump` 也一起拖慢。

### 3.4 当前瓶颈

`count` 之所以仍是主瓶颈，主要因为：

1. 解析阶段很重，尤其是每个 base 的滚动更新。
2. 桶内排序和 RLE 仍然占很大比例。
3. `k21` 的候选项最多，写出和压缩压力最大。
4. 还没有把 SIMD / AVX-512 的收益完整吃满。

所以当前阶段的重点是继续压 parse、sort、rle，而不是改成别的计算模型。

## 4. `dump` 设计

### 4.1 为什么 `dump` 已经能快很多

`dump` 的强项来自结构性设计，而不是单一技巧：

1. 按 bucket 并行处理。
2. 局部段已经有序。
3. 使用败者树做多路归并。
4. `k<=31` 走更紧凑的 `u64` 路径。

这些改造让 `dump` 在 `k31` 和 `k51` 上已经有明显优势，`k21` 则仍需要继续核查回归来源。

### 4.2 `dump` 的重构方向

`dump` 后续只保留能稳定改善吞吐的策略：

1. 并行 bucket 解码与归并。
2. 败者树继续保留，不回退到堆。
3. `k<=31` 继续优先使用紧凑 entry 和快速解码。
4. 写出保持大块顺序输出，避免小块碎片化。

## 5. `.kite` 格式

当前二进制格式按 `k` 选择更紧凑的 entry 宽度：

| `k` 范围 | entry 宽度 |
|---|---|
| `k <= 31` | `u64 + u32`，12 字节 |
| `k > 31` | `u128 + u32`，20 字节 |

原因很直接：如果 `k<=31` 还强制用 `u128`，会增加 segment 体积、压缩成本、磁盘读取成本和 `dump` 的内存带宽压力。

## 6. 当前 benchmark 认知

当前已知的基准结论是：

1. `k31 / k51` 的总时长已经显著领先 KMC。
2. `k21` 已经逼近 KMC，但还不稳定。
3. `count` 仍然是唯一主战场，`dump` 只需要做针对性的修正，不要回退整体结构。

参考已记录的主要结果：

| k | Kite Count(s) | Kite Dump(s) | Kite Total(s) | KMC Total(s) | 结论 |
|---:|---:|---:|---:|---:|---|
| 21 | 259.97 | 14.84 | 274.81 | 275.28 | 基本追平 |
| 31 | 322.39 | 15.94 | 338.33 | 1492.86 | 显著更快 |
| 51 | 507.48 | 24.09 | 531.57 | 1568.00 | 显著更快 |

后续的 test05 又显示，`count` 热路径的局部改造会影响 `dump` 的段规模和 decode 时间，因此优化必须同时看两边，不可只盯一个阶段。

## 7. 下一步

下一阶段只做三件事：

1. 继续压 `count` 的 parse / sort / rle。
2. 针对 `k21` 排查 `dump` 的段规模和 decode 回升原因。
3. 每轮都把 test-mode 指标写回文档，避免只看总时长。

## 8. 验收口径

每轮修改都至少看这些指标：

1. `parse_ms`
2. `sort_ms`
3. `rle_ms`
4. `decode_ms`
5. `tsv_write_ms`
6. `cpu_util_pct`
7. `hottest_partition_segments / least_partition_segments`

只有当这些指标和总时长都没有回退时，才认为改动有效。
